How a task says where it is

3 ways to build the state model, with the real case from your database. 24 Nov 2026.

1. What is broken

A task carries 3 stored facts: status, inbox_reason and current_step. The state machine writes all 3, and only at the moment a step routes. Anything that happens between 2 routings changes nothing. These 5 came out of ~/.orstra/orstra.db this morning.

4 of the 5 share 1 rule. The run row is the only unit of truth, and only the state machine makes one. A chat makes no run. A second turn in an open session makes no record. So real work falls outside the account, and the step keeps pointing at the last thing the machine did.

The 5th is a different rule, same shape. The track is drawn from today's YAML file, while the history is what really ran. Edit the file and the drawing lies about the past.

The run rows and the task fields are 2 records of the same thing, written at different moments by different code. They drift the moment anything happens off the routing path.

A · the runs are the truth, the task state is read from them

Writersroute(), the session layer, your chat
→
runs1 open run per task, each with its own turn state
→
Readersboard, Inbox, run list, chief of staff
  • tasks.status and inbox_reason stop being truth. A read computes them.
  • 1 invariant: a task has at most 1 open run (queued, running or waiting). That run names the step and who holds it.
  • Each run keeps its own live state: the time of its last turn, and whether a turn is in flight. onTurn already fires at every one of those moments, so there is 1 writer.
  • A chat to a run that ended opens a new run of that step. Nothing can happen outside a run.
  • No open run and the plan reached the end means Done. No open run and no end is a bug, and the board says so.

Keeps
  • 1 writer, 1 truth. The run list and the board cannot disagree.
  • Fixes 4 of the 5 rows above.
  • The 27 hour run stops hiding: the card reads its last turn.
  • The merge can ask "is a turn in flight?" and refuse.
Costs
  • A read computes instead of reads 1 field. Cheap, the rows are indexed by task.
  • Every reader changes: board, Inbox, task page, chief of staff, the CLI.
  • The column moves when you chat at a decision. See the fork.

B · the step stays the position, a live state sits next to it

route()writes the step
→
current_step + activity2 fields, 2 writers
→
Readerscolumn from the step, line from the activity
  • tasks gains activity and activity_run_id. The session layer writes them when a session opens, when a turn ends, and when a session dies.
  • The card keeps its column and says who is at work. The decision goes on hold instead of closing.
  • Smallest change of the 3. No reader has to learn the run rows.
Keeps
  • The board's columns stay a map of the plan.
  • The review round keeps the work that was done for it.
  • Least code touched.
Costs
  • 2 writers again. The next thing that happens off the path drifts the same way.
  • It stores liveness in a file on disk. Orstra already lost that bet: recover() exists because rows said running after the process died.
  • The work still gets no run row, so it still has no outcome and no progress entry.

C · the events are the truth, the state is a fold over them

Everythingmessages, tools, decisions, routings
→
eventsappend only, already written today
→
Readersfold the tail into a state
  • Nothing can happen without a record, by construction. The timeline and the board agree because they read the same rows.
  • It is the same screens as A. The difference is the machinery, not what you see.
Why not now
  • The payloads are loose JSON. A typed event schema is its own project.
  • Reads walk hundreds of rows per task, or need a cache, which is a second truth again.
  • A gets most of the gain for a fraction of the work, and C stays open as a later move.

My pick: A. B is this bug again with 1 more field. A gives 1 writer and 1 truth, and every other record in Orstra already hangs off a run, and a run hangs off a step. B is defensible, and it is your product.

6. The other decision in this design

Which workflow does the track draw?
Today it draws from the YAML file as it is now, which is why a task that never merged shows Merge as done. Option 1: pin the workflow version to the task when it starts. Option 2: draw the track from the runs that happened, plus the steps that remain. Pinning changes a rule you chose on purpose, because today an edit to a workflow reaches tasks that already run.
